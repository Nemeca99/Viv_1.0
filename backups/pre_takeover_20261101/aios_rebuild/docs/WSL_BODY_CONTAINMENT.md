# WSL Docker Body Containment

## Architect direction

The deterministic CPU-side AIOS Body runs inside WSL Docker. Viv's GPU-side Mind may propose work to the Body, but must not be able to modify the Body runtime, its image, or its private state. Rust remains the Body authority; Python remains orchestration and learning. This records the Architect's implementation direction and does not revise the locked Hive topology.

## Required containment properties

1. Build the Body from a reviewed, hash-pinned source/image; do not bind-mount its executable code from the Windows workspace at runtime.
2. Run the Body without GPU passthrough, `/dev/dxg`, Docker socket, privileged mode, or extra capabilities; use a non-root container user, read-only root filesystem, bounded CPU/memory/PIDs, and an exclusive Docker-managed state volume only where persistence is required.
3. Keep Docker daemon and WSL command authority outside the Mind. Mind requests cross a narrow, typed broker; the Body accepts no shell, Docker command, arbitrary path, or model-supplied hardware verdict.
4. Keep general network access disabled. If a request channel is needed, expose only the brokered protocol and prove the Mind cannot reach the Docker API or host filesystem through it.
5. Treat host HWiNFO/Corsair readings as external sensor input. A trusted adapter must deliver fresh readings to the Body; the Mind cannot author or overwrite telemetry used for authorization.
6. Verify that a Mind-side compromise cannot write Body files/state, access its Docker control plane, or impersonate fresh telemetry. Docker isolation protects against the contained Mind process, not a Windows administrator or arbitrary code already executing as the same Windows account with WSL access.

## Verification gates

- Inspect the exact Body container configuration and image digest; prove no bind mounts, Docker socket, GPU device, elevated capabilities, or writable code layer.
- Exercise approved and denied Body requests through the broker, including stale/tampered telemetry and attempted shell/path escapes.
- Confirm a Mind-side container cannot read or mutate Body files, state volume, or Docker API; preserve receipts for both allow and deny decisions.
- Run the Rust Body authority and the bounded INN candidate path end to end before claiming WSL Body integration or resuming autonomous learning.

## Current hold

The pinned Body now runs the existing 19-core Python kernel and Rust decision function inside a one-shot WSL Docker invocation, with image-baked code, no GPU passthrough, no host bind mounts, `network=none`, a read-only root, and bounded tmpfs for declared transient paths. Hardware collection, resource snapshots, and Hive orchestration remain Windows-side, and the Body service is not persistent. The sensor adapter supplies host HWiNFO/Corsair/process-resource observations; Rust validates thresholds but cannot independently authenticate their source. The live gate remains HOLD because PrivacyCore does not prove process-wide I/O mediation. Mind-side compromise resistance and same-account WSL/Docker resistance are unproven: the WSL daemon is rootful and reachable from the default WSL identity. The Windows Rust extension remains only for the existing process-bound permit. Do not start candidate training or claim learning is resumed until PrivacyCore/process I/O, trusted sensor/broker provenance, Mind-side denial, and the bounded INN candidate path are verified. Do not change `HIVE_LOCK_MANIFEST.json`, PrivacyCore's allowlist, or candidate admission rules as part of this work.

`main_core.WORKSPACE` now has an opt-in `AIOS_WORKSPACE_ROOT` override for the image-baked kernel; its Windows default is unchanged. One sorted core-discovery helper drives binding and expected-count reporting, replacing the stale `19/13` startup banner with `19/19`. The image imports the existing core modules and tests verify its runtime core inventory matches the embedded Rust manifest. Container log/state paths use bounded tmpfs instead of host mounts. Hardware collection and Hive orchestration still remain on Windows.

`support_core.core.config.AIOSConfig` accepts `AIOS_ROOT`, `AIOS_PYTHON_ENV_PATH`, `AIOS_LOG_DIR`, and `AIOS_DEBUG_DIR` overrides. The pinned container sets these paths, and the live in-container kernel successfully bound all 19 modules without writing host state.
